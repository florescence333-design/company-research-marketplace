# 기업분석 플러그인 설계서 v1 (미국주식·웹 게시)

Oct 6, 2026 · @김지원

## 한눈에 보기

**현재 구현 상태(2026-10-06):** 1단계의 데이터 계약은 **v1 초안**이며, 4단계 RKLB 실제 공시의 구조·재계산 검증을 통과한 뒤에도 다른 기업·공시 본문 검증 전까지 초안으로 둔다. 이번 일정에는 세부 판정 규칙을 구현하지 않고 모든 실행의 최종 판정을 **판정 보류 (v0.1)**로 고정한다. 아래 판정 기준 v1은 향후 구현 설계이다.

**진행 기록:** 4단계에서 RKLB 실제 SEC Company Facts가 v1 초안의 구조·원본 재계산 검증을 통과했다. 스키마는 다른 기업·공시 본문·후속 분석을 확인할 때까지 계속 초안으로 유지한다. 사용자 일정에 따라 이번 구현에서는 5단계의 판정 엔진을 건너뛰고 16단계 분석의 단순한 연결부터 진행한다.

미국 티커 하나(`/company RKLB`)를 넣으면 실행 환경의 AI가 16단계 기업분석 보고서·항목별 평가·도식을 만들고, 코드가 재무 지표와 최종 판정을 계산하는 플러그인이다. 자동 검증을 통과하면 게시 설정에 따라 비공개 웹사이트에 게시하거나 로컬 미리보기를 만든다. 개발은 Codex에서 하고, 분석은 Claude Code(Claude판)와 Codex(GPT판) 양쪽에서 실행한다. 이 문서의 명령어는 논리적 호출명이며, 설치 환경별 실제 호출 표기는 초기 호환성 확인에서 확정한다.

## 범위

v1은 강의 과제용 웹 게시 버전이며, 옵시디언을 원본으로 쓰는 버전은 별도 플러그인으로 나중에 만든다.

**포함**

- 미국 상장사 중 10-K·10-Q를 제출하는 US-GAAP 비금융 일반 기업 분석 (사용자 확정)
- 16단계 Master Template 기반, 기업별 자동 커스텀 템플릿
- 지정된 재무 지표 12종 자동 계산 + 분석일 기준 스냅샷
- 플라이휠·밸류체인 도식, 3년 재무 추이 차트(재무 탭)
- Claude판·GPT판 동시 게시, 전환·비교
- 자동 검증 후 자동 게시와 배포 완료 확인, 운영·미리보기 모두 비밀번호 보호
- 코드 기반 두 축 판정, 항목별 두 엔진 비교, 판정 보류 상태

**제외 (v1)**

- 한국 주식 (DART 연동)
- 신규 상장사, 금융사·REIT·펀드·SPAC 등 일반 비금융 영업회사에 해당하지 않는 대상, 20-F·6-K/IFRS 대상
- Holder 탭 (기관·펀드 보유자)
- 경쟁사 재무 비교 차트
- 날짜별 버전 비교 화면, 이전 대비 변경 요약
- 개인별 로그인·이메일 인증 (공용 비밀번호 하나만 사용)
- 로그인 실패 횟수 제한과 이를 위한 별도 Worker·Durable Object (나중에 검토)
- 실시간 시세 칸 (호가, 거래량, 당일 범위 등)
- 애널리스트 1년 목표주가
- 사용자용 게시 없는 테스트 실행 옵션 (개발·검증은 `dev` 브랜치의 Cloudflare 미리보기 사용)

**적합성·지원 범위**

- S0에서 티커를 CIK·거래소·주식 종류와 연결하고 공시 형식, 회계기준, 업종, 확보 가능한 기간을 확인한다. 티커만으로 기업·증권을 동일시하지 않는다.
- **사용자 확정:** v1은 10-K·10-Q를 제출하는 US-GAAP 비금융 일반 기업으로 제한한다. 신규 상장사는 분석을 시도하지 않고 '지원 범위 밖'과 사유만 안내한다.
- **v1 기본값 (Codex 제안):** 신규 상장사 제외의 운영 기준은 기존 문서의 '상장 후 10-K로 확보한 4개 회계연도 미만'을 사용한다. 제출 문서 개수가 아니라 공시로 확보되는 서로 다른 회계연도를 센다. 상장신고서로 부족한 기간을 보충하지 않는다. 금융사·REIT·펀드·SPAC과 다른 공시·회계기준 대상도 제외하며 분류 불명확 시 적합성 확인 실패로 중단한다. 이 운영 기준은 4단계 실제 기업 검증에서 조정할 수 있다.
- 지원하지 않는 대상은 사유를 표시하고 중단한다. 지원 대상의 일부 값이 없는 경우에는 데이터 상태와 판정 보류 규칙으로 처리한다. 두 경우를 혼동하지 않는다.
- 지원 범위 밖 대상은 평가상 '회피'와 구분하고 기존 게시본도 변경하지 않는다.

**기술 기본값의 관리**

이 문서에서 **v1 기본값 (Codex 제안)**으로 표시한 값은 보수적인 프로젝트 시작값이며, 업계에 단 하나의 정답이 있다는 뜻은 아니다. 실제 데이터·설치·배포 검증에서 문제가 발견되면 변경 근거와 검증 사례를 남겨 조정할 수 있다. 설정·공급자 어댑터로 분리하고 `technical_defaults_version`과 계산 코드 버전을 실행 결과에 기록한다. 기존 실행의 입력·설정은 소급 변경하지 않는다. 판정 기준 v1과 사용자 확정 지원 범위는 별도 관리한다.

## 명령어와 실행 흐름

분석 명령은 `/company`, 재검증·게시 명령은 `/company-publish`로 둔다. 분석에서 무엇을 빼거나 바꿀지는 옵션으로 붙인다. 옵션은 조합할 수 있다(예: `--original --no-viz`). 사용자용 테스트 옵션은 추가하지 않는다.

| 입력 | 하는 일 |
| --- | --- |
| `/company RKLB` | 기본 과정. 적합성 검토 → 기업 맞춤 템플릿 설계 → 분석 → 시각화 → 검증 → 게시. 중간에 사용자 확인 없음 |
| `/company RKLB --no-viz` | 시각화를 빼고 분석까지 게시. 시각화 탭에는 "미생성" 표시 |
| `/company RKLB --viz-only` | 해당 엔진의 기존 완료 분석을 바탕으로 도식만 다시 생성·검증·게시. 기준 보고서의 run_id·해시를 기록하고, 기존 분석이 없거나 게시 직전 기준본이 바뀌면 중단 |
| `/company RKLB --original` | 커스텀 없이 원본 Master Template으로 분석. 기업 간 비교용 |
| `/company RKLB --new` | v1 기본값 (Codex 제안): 이어하기 대신 새 기준시점·run_id로 분석 시작. 테스트 옵션이 아님 |
| `/company RKLB --run-id <id>` | v1 기본값 (Codex 제안): 같은 기업·엔진의 지정 실행을 재개. --new와 동시 사용 불가 |
| `/company-publish RKLB` | 해당 엔진의 게시 대상 실행을 식별해 다시 검증·게시. 후보가 모호하면 임의 선택하지 않고 안내 |
| `/company-publish --site` | 분석 없이 화면 코드만 검증·반영하고 배포 완료 확인. 기존 데이터와의 스키마 호환성도 확인 |

**Codex에서 실행할 때**

Codex의 논리적 호출 예시는 `$company RKLB --no-viz`이다. 공통 옵션 의미는 공유하고, 실제 옵션 파싱·검증은 공통 스크립트가 수행한다. 환경별 설치 후 노출되는 스킬명·플러그인 네임스페이스·호출 문법은 초기 확인에서 기록한다. 엔진은 실행 환경 어댑터가 기록한다(Claude Code → `claude`, Codex → `gpt`). 실제 모델 식별자를 확인할 수 있으면 별도로 기록하고, 확인할 수 없으면 추정하지 않는다. 한 엔진으로 다시 실행하면 그 엔진 결과만 교체하고 다른 엔진 결과는 그대로 둔다.

**지침 정리 사항**

- 기존 지침의 단계별 대기(`/template` → 진행 → Go)와 트리거 불일치는 폐기한다. 적합성 검토와 커스텀은 사용자 응답 없이 자동으로 이어진다.
- `/flywheel`은 폐기하고 `--viz-only`로 통합한다.
- 명령어 없이 티커만 오면 `/company` 사용법만 안내한다.
- 섹션 합치기·생략·조기 종료 금지는 고정 ID와 구조화 응답을 S6에서 검사한다. 코드가 내용의 진실성까지 보장한다고 표현하지 않는다.
- 사용자용 게시 없는 테스트 옵션은 두지 않는다. 개발·검증은 `dev` 미리보기에서 수행하고 운영 반영 실패 시 기존 정상본을 유지한다. 깃 이력 복구는 사후 복구 수단으로 둔다.
- **v1 기본값 (Codex 제안):** `--no-viz`+`--viz-only`, `--viz-only`+`--original`, `--new`+`--run-id`는 잘못된 조합으로 안내하고 실행하지 않는다. 도식만 바꾸는 명령에서 템플릿·분석 기준시점을 함께 바꾸지 않는다.

**커스텀 템플릿 규칙**

- 16개 대섹션의 번호와 제목은 그대로 유지한다. 섹션을 합치거나 빼지 않는다.
- 섹션 안의 내용(세부 항목, 체크리스트, 지표)은 그 기업에 더 맞게 수정·추가·교체할 수 있다.
- 결과물은 `template.md`(표시용), `template-items.json`(세부 항목별 고정 ID·필수 여부·응답 형식), `template-notes.json`(원본 대비 바뀐 항목과 이유)으로 남기고 템플릿 탭에 게시한다.
- 세부 응답은 `report-items.json`에 항목 ID·응답·상태·출처 ID·지표 참조를 기록한다. 코드가 이 구조에서 `report.md`를 조립한다. AI는 응답 본문을 작성하되 섹션 구조와 수치 렌더링을 임의 변경하지 않는다.
- 검증 단계는 16개 섹션 ID의 누락·중복·순서, 필수 세부 항목의 응답과 근거 존재를 확인한다. 응답의 충실성과 근거가 주장을 지지하는지는 별도 근거 검토로 다룬다.
- 16단계 Master Template 최종본: **입력 완료**. 원본 `docs/020. 기업분석_Master Template.md`; 최상위 16개 섹션 ID·제목은 `template/sections.json`에 추출했다.
- 투자 프레임워크 v2: **입력 대기**.

**Pro 요금제 대응**

한 번에 16개 섹션을 쓰면 사용량 한도에 걸릴 수 있으므로 섹션 묶음 단위로 실행하고 단계마다 체크포인트를 남긴다. 체크포인트는 한도를 늘리거나 자동으로 해제하는 기능이 아니다. 실행을 다시 시작했을 때 유효한 완료 단계만 재사용한다.

**실행·이어하기 계약**

- 실행별 `run_id`, `analysis_as_of`(정보 기준시점), `data_snapshot_id`, 엔진, 옵션, 코드·스키마·템플릿·판정 기준 버전, 단계별 입력·출력 해시와 상태를 `run.json`에 저장한다.
- 작업 중 산출물은 `runs/<티커>/<엔진>/<run_id>/`에 저장한다. 검증 전 결과를 게시용 `data/`에 직접 덮어쓰지 않는다.
- 단계 상태는 `pending / running / completed / failed / blocked`로 구분한다. 파일이 있다는 이유만으로 완료 처리하지 않고 출력 해시와 단계 검증 결과를 확인한다.
- 완료 단계라도 입력이나 관련 버전이 달라지면 그 단계와 의존하는 후속 단계는 재실행한다. 기준시점·스냅샷을 바꾸려면 새 실행으로 취급하고 서로 다른 시점의 결과를 섞지 않는다.
- **v1 기본값 (Codex 제안):** 같은 티커·엔진·분석 옵션·관련 버전으로 시작한 24시간 이내 미완료 실행이 하나이면 고정된 기준시점을 알리고 재개한다. 없으면 새 실행을 만든다. 후보가 여러 개이면 임의 선택하지 않고 `--run-id` 지정을 안내한다. `--new`는 새 분석을 강제한다. 지정 실행에서도 해시 검증·후속 단계 무효화는 유지한다.
- **v1 기본값 (Codex 제안):** `/company-publish RKLB`는 해당 엔진의 가장 최근 생성된 비실행중 산출물 묶음을 대상으로 재검증한다. `--run-id <id>`로 대상을 명시할 수 있다. 실행중인 게시 후보·생성시각 동률·대상 불일치는 중단하며, 최신 기준시점 보호 규칙은 명시 실행에도 적용한다.
- 데이터가 부족해 `판정 보류`가 된 완성 보고서와, 처리 실패로 미완성인 실행을 구분한다. 전자는 상태·사유를 명시해 검증할 수 있지만 후자는 게시하지 않는다.

## 파이프라인 (S0\~S7)

기존에 누락된 임베드 도식 대신 단계별 입출력과 실패 처리를 표로 정의한다. 정상 경로는 중간 확인 없이 진행하되, 미정 규칙·필수 입력·권한 문제는 기록하고 관련 단계에서 멈추거나 명시된 보류 규칙을 적용한다.

| 단계 | 입력·처리 | 출력 | 실패·보류 처리 |

## 재무 지표 계산 사양

12개 지표는 확보 가능한 XBRL 원본을 우선 사용하고, 모든 계산은 코드가 수행한다. 순이익의 질·부채 구조·금리 비중의 누락 수치는 공시 본문 판독이 필요할 수 있다. AI의 본문 추출값은 근거와 함께 별도 저장하고 검증을 통과한 값만 계산 입력으로 사용한다. "3년 분석"에서 전년 대비 성장률 3개를 내려면 **4개 회계연도** 데이터를 받는다. 판정의 필수 입력인 '3년 재무'와 성장률 계산에 필요한 4년 입력은 별도 요건으로 구분한다.

| 지표 | 데이터 출처 | 계산 방식 |
| --- | --- | --- |
| 매출 성장률 | XBRL 매출 태그 | 전년 대비 증가율 3개 + 3년 연평균(CAGR) |
| 영업이익률 | XBRL 영업이익, 매출 | 영업이익 ÷ 매출 |
| 순이익의 질 | XBRL + 10-K 본문 | ① OCF ÷ 순이익(순이익이 양수일 때 해석) ② 검증된 일회성 조정 내역과 순이익 비교 ③ 영업외 손익 비중 ④ MD&A의 일회성 이벤트 확인. 적자·분모 0은 일반 비율과 구분 |
| 부채비율 | XBRL 총부채, 자기자본 | 총부채(liabilities) ÷ 자기자본. 자기자본이 0 이하이면 비율 대신 상태·경고 표시 |
| 현금·현금성 자산 | XBRL | 기말 잔액 + 단기투자 별도 표기 |
| 유동자산 회전율 | XBRL 매출, 유동자산 | 매출 ÷ 평균 유동자산(기초·기말 평균) |
| 부채 구조 | XBRL 만기 태그 우선, 없으면 10-K 부채 주석 | 단기·장기 비중, 1\~5년차·5년 이후 만기 분포, 순현금(현금·단기투자 − 총차입금), 단기차입(CP) 증감 |
| 금리 비중 | 10-K 부채 주석, Item 7A(시장위험) | 변동·고정 금리 비중, 표면금리 범위, 헤지 여부, 선순위·담보 여부, 10-K에 언급된 신용등급. 출처 문단 인용 |
| OCF 성장률 | XBRL 영업현금흐름 | 전년 대비 증가율 3개 |
| CapEx vs OCF | XBRL 유형자산 취득, 영업현금흐름 | CapEx ÷ OCF, 잉여현금흐름(OCF − CapEx) |
| 재고 vs 매출 증가 속도 | XBRL 재고자산, 매출 | 두 증가율의 차이 (재고가 매출보다 빠르면 경고) |
| 매출채권 vs 매출 증가 속도 | XBRL 매출채권, 매출 | 두 증가율의 차이 (채권이 매출보다 빠르면 경고) |

**구현 규칙**

- 기업마다 XBRL 태그 이름이 다르므로 지표별 우선 태그·대체 태그와 **동일한 경제적 의미인지 확인하는 조건**을 함께 둔다. 후보가 있어도 기간·통화·단위·연결 범위가 다르면 바로 대체하지 않는다. 표준 태그로 확보할 수 없는 상세 주석·기업 전용 태그는 공시 본문 추출 경로로 넘기고, 근거를 확보하지 못하면 "확인 불가"로 둔다.
- 수치 선택 키에는 CIK, taxonomy·tag, 기간 시작·종료일 또는 시점, 통화·단위, 연결 범위·차원 정보, form, accession number, 공시 제출·접수 시점을 포함한다. 연간·분기·누적·시점 값을 구분하고 `fy`나 `fp`만으로 기간을 판단하지 않는다.
- `analysis_as_of`까지 공개된 공시만 사용한다. 같은 의미·기간·단위·범위의 값이 여러 공시에 있을 때 그 기준시점 내 최신 유효 값을 고르고 원 공시·정정 공시와 선택 사유를 남긴다. 10-K/A 등이 있다고 모든 항목을 무조건 교체하지 않는다.
- 여러 연도를 잇는 경우 재작성·사업 매각·회계기준 변경에 따른 비교 가능성을 검사하고, 조정 전·후 값을 섞으면 사유와 한계를 표시한다. 원본 캐시와 해시를 보존해 선택 결과를 재현할 수 있게 한다.
- 회계연도는 "FY2025 (2024년 10월\~2025년 9월)"처럼 기업 회계연도와 실제 기간을 함께 표기한다.
- 모든 수치는 어느 공시의 어느 태그·표·문단에서 왔는지 `sources.json`에 기록한다. 본문 추출은 인용 구절, 표 제목·행·열 또는 문단 위치, 원 단위, 정규화 값, 검증 상태를 `extracted-facts.json`에 남긴다.
- SEC 요청에는 연락 가능한 이름·이메일이 담긴 User-Agent를 사용한다. 값은 Windows 사용자 범위 `SEC_USER_AGENT` 환경변수에서 실행 프로세스로 읽고, 코드·설정 파일·로그·대화에 기록하거나 출력하지 않는다.
- 수집기는 캐시·요청 속도 제한·재시도를 두고 403·429·네트워크 실패를 '해당 없음'으로 바꾸지 않는다. 외부 문서 내용은 데이터로 취급하며 도구 실행·비밀 값 전송 지시로 따르지 않는다.

**계산 예외와 용어**

- **v1 기본값 (Codex 제안):** 총부채(liabilities)와 총차입금을 분리한다. 총차입금은 단기차입·CP·유동성 장기차입·장기차입·금융리스부채를 포함하고 중복 합산하지 않는다. 운용리스부채는 별도 표시하며 기본 순현금 계산에서는 제외한다. 리스 포함/제외 금액과 선택 근거를 남긴다. 역DCF의 순차입금 처리 방식은 판정 세부 TODO로 별도 보류한다.
- 성장률은 전기 값이 양수이고 부호가 바뀌지 않는 정상 범위에서 일반 공식을 사용한다. 전기 값 0·음수·부호 전환은 '계산 불가' 또는 '적자 축소/확대·흑자/적자 전환' 등 상태와 절대 증감을 우선 표시하고 일반 성장률로 오해하게 하지 않는다. 음수 OCF가 개선된 경우를 성장 악화로 자동 판정하지 않는다.
- CAGR은 필요한 전체 기간을 확보하고 시작·종료 값이 양수일 때 계산한다. 분모가 0인 비율은 null과 사유를 기록한다. OCF·순이익이 음수인 비율은 현금창출력·이익의 질을 나타내는 정상 비율처럼 평가하지 않는다.
- 재고·매출채권이 없거나 업종상 적용되지 않으면 0으로 채우지 않고 `not_applicable`로 둔다. 적용 여부를 확인하지 못하면 `unavailable`로 구분한다.
- **v1 기본값 (Codex 제안):** GAAP 순이익을 기본값으로 유지한다. 일회성 조정은 공시에서 사건·금액·세효과를 명확히 확인한 항목만 별도 계산하고, 세효과가 없으면 세율을 추정하지 않아 조정 순이익 총액은 확인 불가로 둔다. 손상·매각손익·평가손익도 자동 제외하지 않고 확인 근거를 남긴다. 주식보상과 반복 구조조정을 관행적으로 더하지 않는다. 영업외 손익 비중은 순영업외손익 ÷ 세전이익으로 계산하되 세전이익이 0 이하이면 비율 대신 금액·상태를 표시한다. 회계 품질 경고 정의는 판정 섹션의 TODO에 따르며 **구축 순서 5단계 전 결정**한다.
- **v1 기본값 (Codex 제안):** 계산은 원정밀도로 수행한다. 표시값은 주가·EPS·배당금 2자리, 백만 단위 재무 금액 1자리, 백분율·%p 1자리, 배수·베타 2자리로 반올림하고 단위를 명시한다. 코드 재계산은 Decimal 기준으로 대조하고 표시값은 마지막 표시 단위의 절반까지만 반올림 오차로 허용한다. 원공시와의 대조는 공시된 반올림 단위의 절반 및 연산에 따른 오차 전파 범위만 허용하며, 단위가 불명확하면 검증 실패로 둔다. 임의의 일괄 1% 허용 오차는 두지 않는다.

**분석 기준 스냅샷 값의 출처**

**EPS(TTM)·시장 데이터 보완 규칙**

- 기본 EPS(TTM)는 동일 주식 종류·통화·분할 기준의 **최근 연속 4개 독립 분기 희석 EPS 합계**로 정의하고 계산 방법을 저장한다. 연간 EPS에서 9개월 누적 EPS를 차감해 4분기 EPS를 만들지 않는다. 분기 합계와 공시 연간 EPS가 다를 수 있음을 표시한다.
- 분기 희석 EPS 4개를 확보하지 못하면, 검증 가능한 TTM 순이익과 최근 공시의 희석 가중평균 주식 수로 근사한다. 분자·분모의 기간·기준일·출처를 모두 표시하고 기간 불일치에 따른 한계를 남긴다. 필요한 값이 없거나 분모가 0 이하이면 근사도 하지 않고 `unavailable`로 둔다.
- **v1 기본값 (Codex 제안):** EPS 근사 분자는 보통주 귀속 TTM 순이익으로 하고 비지배지분·우선주 배당을 구분한다. 공시된 희석 분자 조정이 필요하지만 재현할 수 없거나 주식 종류별 이익 배분이 불명확하면 근사하지 않는다. 분모는 최신 공시의 독립 분기 희석 가중평균 주식 수를 우선하고, 없으면 같은 최신 보고기간의 누적 또는 연간 값을 사용해 그 기간을 표시한다. 분모 기간 종료일부터 기준시점까지 135일을 넘으면 근사하지 않는다. 이 135일은 판정에 필요한 '3년 재무' 신선도 규칙을 대신하지 않는다.
- 순이익 등 가산 가능한 금액의 분기·TTM 재구성은 같은 회계 범위의 기간을 맞춰 수행한다. EPS와 가중평균 주식 수에는 금액 차감 규칙을 그대로 적용하지 않는다.
- 주식분할·증자·복수 주식 종류를 고려한다. 경제적 권리나 가격이 다른 종류의 주식에 하나의 가격을 일괄 곱하지 않는다. 발행주식수와 EPS용 가중평균 주식 수도 혼용하지 않는다.
- 주가 API 키가 없거나 호출에 실패하면 상태·사유를 기록하고 확보된 재무·보고서 작업은 계속할 수 있다. 최종 판정은 확인된 강제 회피 조건을 먼저 적용하고, 해당 조건이 없으면 필수 주가 누락으로 판정 보류한다. 주가가 없다는 사실 자체를 위험 신호로 취급하지 않는다.
- **v1 기본값 (Codex 제안):** 주가 기본 공급자는 Twelve Data, 기본 경로는 무료 계정에서 허용되는 `/time_series` 일별 데이터로 한다. 캐시를 공유하고 공급자별 어댑터를 둔다. 무료 권한·조회 기간·분할 조정·수업 열람 및 웹 표시 이용 범위를 초기 실제 데이터 검증에서 확인한다. 비공개 사이트라는 이유만으로 재배포 권한을 가정하지 않는다. 권한·이용 조건을 충족하지 못하면 해당 데이터를 게시하지 않고 공급자 변경을 검토하며 자동 유료 전환이나 비공식 스크래핑은 하지 않는다. 키 없음·권한 부족·데이터 부족은 확인 불가로 처리한다.
- **v1 기본값 (Codex 제안):** 주가는 기준시점까지 확정된 최근 정규 거래일 종가를 사용한다. 최대 1개 완료 거래세션까지 이전 값은 '최신 종가 아님'과 실제 거래일을 표시해 허용하고, 더 오래되면 판정용 주가는 확인 불가로 둔다. 시간대·휴장일·서머타임을 반영한다. 시가총액 주식 수는 기준일이 135일 이내인 최신 보통주 발행주식수를 사용하고 이후 분할·증자를 확인한다. 기업행사를 반영할 수 없으면 시가총액을 확인 불가로 둔다.
- **v1 기본값 (Codex 제안):** 52주 범위는 직전 52주의 분할 조정 일별 고가·저가로 계산하고 배당은 가격에서 조정하지 않는다. 현재 주가와 EPS·주식 수는 같은 분할 기준으로 맞춘다. 배당수익률은 최근 12개월 보통 현금배당(특별배당 별도 표시, 주당 금액은 분할 반영) ÷ 기준 종가로 계산한다. 완전한 배당 이력을 확보하지 못하면 0% 대신 확인 불가로 표시한다.
- **사용자 확정:** 구축 순서 2단계에서 Twelve Data 무료 요금제의 배당 이력·실적 발표 일정 제공 여부를 각각 실제 계정 권한·응답으로 확인하고 기록한다. 미제공이면 배당 이력은 SEC 공시, 실적 발표일은 웹 리서치(기업 IR의 확인된 일정 우선)로 대체한다. 공시 배당은 주당 금액·기간·종류·분할 기준과 출처를 검증하며, 총 배당금만으로 주당 배당이나 배당락일을 추정하지 않는다. 발표일은 확정/예정 여부·기준시점을 기록하고 추정 날짜를 확정 일정으로 표시하지 않는다. 대체 출처에서도 확인할 수 없는 항목은 확인 불가로 둔다. 무료 미제공과 수집 실패는 구분해 기록하고, API를 대체한 경우 공급자·대체 사유·출처를 남긴다.
- **v1 기본값 (Codex 제안):** 베타는 SPY와 대상 주식의 같은 월말 분할 조정 종가 61개로 구한 60개 단순 월간 가격수익률의 공분산 ÷ SPY 수익률 분산으로 계산한다. 진행중인 달은 제외하고 배당 재투자는 포함하지 않음을 표시한다. 60개 짝이 없거나 SPY 분산이 0이면 확인 불가로 두며 더 짧은 기간으로 임의 대체하지 않는다.

**신규 상장사 처리 — v1 제외**

사용자 확정에 따라 S0에서 **'지원 범위 밖: 신규 상장사는 v1에서 지원하지 않음'**으로 안내하고 종료한다. S-1·424B4 추출, 신규 상장사 전용 계산·판정·게시를 진행하지 않는다. 이미 지원되는 기업의 기간 누락을 신규 상장으로 잘못 분류하지 않도록 상장 정보와 공시 이력을 함께 확인한다.

**지표별 분석 (AI)**

숫자는 코드가, 해석은 AI가 맡는다. AI는 코드가 만든 `metrics.json`을 읽고 지표마다 분석 문단을 써서 `financials-analysis.json`에 저장한다. 같은 분석을 재무 탭과 보고서의 재무 섹션에 함께 쓰므로 한 번만 작성한다.

- 지표별 수치 줄(연도별 추이)은 코드가 `metrics.json`에서 자동으로 만든다. AI는 숫자를 다시 타이핑해 옮기지 않는다.
- 분석 문단은 왜 그런 숫자가 나왔는지를 10-K MD&A·주석과 웹 자료로 설명한다 (예: 인수로 인한 현금 감소, 사업 구성 변화로 인한 재고 감소).
- 판단 문장에는 \[해석\]을 달고, 판단마다 틀릴 수 있는 조건을 한 줄 붙인다. "우려가 전혀 없다" 같은 단정 표현은 쓰지 않는다.
- 분석 문단의 재무 수치는 가능한 한 `metric_id`·기간·표시 형식 참조로 넣고 코드가 렌더링한다. 자유문장의 숫자는 지표 또는 별도 출처와 연결하고 S6에서 단위·기간·반올림까지 대조한다.
- 부채 구조와 금리 비중은 심층 항목으로 쓴다: 순현금, 만기 분포, 고정·변동 금리와 표면금리 범위, 선순위·담보 여부, 신용등급(10-K 언급 시), 단기차입 증감.
- 마지막에 재무 종합 요약 한 단락을 둔다.

## 판정 기준 — 사업 품질과 가격의 두 축

**판정 기준 버전: v1. 실제 결과 검토 후 조정 예정.** 아래 값과 규칙은 v1 기본값이며 실제 기업 분석 결과를 검토한 뒤 버전을 갱신해 조정한다. 과거 결과의 기준 버전과 입력은 보존한다.

AI는 사업 품질의 점검 항목별로 **강함 / 보통 / 약함**, 근거, 틀릴 수 있는 조건을 작성한다. 출처·지표 ID를 근거에 연결하며 최종 매수·관망·회피 판정을 직접 작성하거나 덮어쓰지 않는다. 가격 축에서는 **달성 가능한 성장률의 하단 / 기본 / 상단**과 근거·틀릴 수 있는 조건을 제시한다. 코드는 역DCF 요구 성장률과 그 범위를 비교해 가격 축을 분류하고 사업 품질 종합 및 최종 판정을 수행한다. **점수 평균은 쓰지 않는다.**

### 축 A: 사업 품질

| 고정 항목 ID | 점검 항목 | 평가 결과 |
| --- | --- | --- |

| financial_stability | 재무 안정성 | 강함 / 보통 / 약함 + 근거 + 틀릴 수 있는 조건 |
| moat_bottleneck | 경쟁우위·병목 | 강함 / 보통 / 약함 + 근거 + 틀릴 수 있는 조건 |

- 항목 ID는 엔진과 커스텀 템플릿이 달라도 유지한다. 근거 부족이면 평가를 억지로 채우지 않고 해당 항목의 평가를 null, 상태를 `unavailable`로 둔다.
- 코드의 v1 종합 규칙은 다음 순서로 적용한다. ① **회계 품질 또는 재무 안정성 중 하나라도 약함**, 또는 **약함이 2개 이상**이면 축 A는 **약함**. ② 그 외에 **약함이 없고 강함이 3개 이상**이면 **강함**. ③ 나머지는 **보통**. 항목 평가를 숫자로 바꾸어 평균내지 않는다.
- 종합 규칙은 다섯 항목의 유효한 평가에 적용한다. 누락된 평가를 보통으로 채우거나 '약함이 없음'으로 간주하지 않는다. 미완성 평가와 필수 입력 누락은 구분해 검증한다.
- AI가 기업 유형을 근거와 함께 분류하고 `assessments.json`에 기록하며 **템플릿 탭에 기업 유형·분류 근거·적용 잣대·판정 기준 버전 v1을 표시**한다. 유형별 분기는 공통 필수 입력·강제 회피 조건을 해제하지 않는다.

### 축 B: 가격

- 코드는 현재 주가와 고정된 재무 스냅샷·가정으로 역DCF를 풀어 현재 가격이 요구하는 성장률을 계산한다. v1은 **할인율 10% 고정, 영구성장률 2.5%, 예측 기간 10년**을 기본으로 한다.
- **할인율 9%와 11%**에서도 같은 입력·영구성장률·예측 기간으로 계산한 결과를 함께 표시한다. 기본 가격 축·최종 판정은 10% 결과를 사용하며 9%·11%는 민감도 결과로 분리한다. 계산하지 못한 시나리오는 사유를 표시하고 기본 결과로 대체하지 않는다.
- AI는 달성 가능한 성장률 **하단 / 기본 / 상단**을 수치와 근거·틀릴 수 있는 조건으로 제시한다. 역DCF가 요구하는 성장률과 같은 성장 대상·기간·단위를 사용하고 `하단 ≤ 기본 ≤ 상단`을 만족해야 한다. AI가 역DCF 계산값이나 고정 가정값을 바꿔 넣지 않는다.
- 코드는 반올림 전 요구 성장률 `g_required`를 아래 경계에 적용해 가격 축을 결정한다. 하단·기본과 같은 값은 **적정**에 포함한다. 상단은 시나리오 설명과 비교용이며 v1 가격 등급의 별도 경계로 사용하지 않는다.

| 조건 | 코드의 가격 축 결과 |
| --- | --- |
| g_required < 하단 | 여유 있음 |
| 하단 ≤ g_required ≤ 기본 | 적정 |
| g_required > 기본 | 과도 |

### 적용 순서와 강제 회피

v1 적용 순서는 **강제 회피 → 판정 보류 → 판정표**이다.

1. **강제 회피:** 확인된 데이터로 아래 조건 중 하나라도 충족하면 `회피`이다. 다른 필수 입력이 부족하더라도 확인된 강제 회피가 우선한다.
2. **판정 보류:** 확인된 강제 회피 조건이 없고, 필수 입력인 **주가, 3년 재무, 역DCF 계산 가능 여부** 중 하나라도 충족하지 못하면 `판정 보류`이다. 정보 부족을 관망이나 위험으로 바꾸지 않는다.
3. **판정표:** 앞 두 단계에 해당하지 않고 두 축의 유효한 결과가 준비되면 판정표를 적용한다.

| 강제 회피 조건 | 확인·기록할 내용 |
| --- | --- |
| 회계 품질 경고 2개 이상 | 경고별 고정 ID·근거·적용 규칙. 같은 원인의 반복 기록으로 개수를 늘리지 않음 |
| 유동성 위기 신호 | 확인된 신호와 원천 데이터·기준시점 |
| 감사인의 계속기업 불확실성 의견 | 감사인 보고서의 해당 의견·공시·근거 위치 |
| 최근 3년 내 재무제표 정정 | 분석 기준시점 기준 최근 3년의 정정 사실·공시일·대상 재무제표. 단순 서류 수정 여부와 구분 |
| 내부통제 중대한 취약점 보고 | 해당 보고·공시·근거 위치 |
| 적자 기업의 현금 소진 기간 12개월 미만 | 적자 여부, 현금 소진 기간의 계산 입력·산식·기준시점. 12개월과 같으면 이 조건으로 발동하지 않음 |

- 강제 회피는 **확인된 데이터로만 발동**한다. 자료 없음·수집 실패·불확실을 위험의 확인으로 바꾸지 않는다. 각 조건에 확인 상태와 출처를 기록하며, 미확인은 '위험 없음이 확인됨'과도 구분한다.
- 강제 회피가 확정되면 산출하지 못한 축·역DCF 값은 null과 사유로 남길 수 있다. 코드는 다른 입력 누락 때문에 확인된 회피 결론을 보류로 바꾸지 않는다. 게시 검증은 회피 근거와 조건부 필수 필드를 검사하고, 계산 불가능한 값을 억지로 채우게 하지 않는다.

### 코드가 적용하는 판정표

아래는 **v1에서 그대로 사용하는 판정표**이다. 강제 회피·판정 보류에 해당하지 않고 두 축이 유효하게 확정된 경우에 적용한다.

| 축 A 사업 품질 | 축 B 여유 있음 | 축 B 적정 | 축 B 과도 |
| --- | --- | --- | --- |
| 강함 | 매수 검토 | 매수 검토 | 관망 |
| 보통 | 관망 | 관망 | 회피 |
| 약함 | 회피 | 회피 | 회피 |

- 판정표 칸은 v1에서 변경하지 않는다. **실제 결과 검토 후 조정 예정**이며 변경 시 새 판정 기준 버전으로 기록한다.
- 코드는 최종 판정, 적용한 우선 규칙 또는 표의 칸, `decision_policy_version: v1`, 입력 데이터 식별자, 항목·축별 결과를 함께 기록한다. AI가 작성한 최종 판정 문자열을 신뢰해 게시하지 않는다.
- v1의 미지정 세부 계산·평가 기준을 확정하기 전에는 합성 샘플로 해당 UI를 시연할 수 있으나 실제 투자 판정처럼 표시하지 않는다. 세부 기준 미정과 실제 데이터 부족에 따른 `판정 보류`는 구분한다.

| sources.json | 고정 source_id, URL·제목·게시/접수 시점·접근 시점, 공시 번호·태그 또는 표/문단 위치, 원본 해시·근거 구절. 보고서 주장·수치와의 참조 관계 |

- 공통 데이터 상태는 `ok / not_applicable / unavailable / collection_failed`로 구분한다. 근사 여부는 상태와 별도 필드로 두어, 근사값이라도 유효한 값과 수집 실패를 혼동하지 않는다. 누락은 null과 이유로 표현하고 0이나 빈 문자열로 대체하지 않는다.
- 날짜·시간은 시간대를 명시하고 숫자에는 단위·기간을 붙인다. `analysis_as_of`, 주가 거래일, 재무 기간, 실행 완료일은 서로 다른 필드이다.
- `data_snapshot_id`는 선택한 입력 원본과 정규화 결과를 식별한다. 코드·템플릿·판정 기준 버전은 별도로 기록한다. 같은 코드라는 이유로 서로 다른 스냅샷을 동일 입력으로 취급하지 않는다.
- 모든 참조 ID는 실제 대상에 연결되어야 한다. 판정·대시보드·보고서·재무 탭은 같은 지표와 `decision.json`을 참조해 값과 결론의 불일치를 막는다.
- v1의 세부 계산 가정과 기업별 AI 성장률 범위는 별도 저장해 결과를 재현할 수 있게 한다. 판정 기준 안내에는 **'실제 결과 검토 후 조정 예정'**을 표시한다. 강제 회피가 먼저 확정된 경우 미산출 축·역DCF 필드를 null과 사유로 허용하도록 조건부 스키마를 둔다.
- JSON Schema의 필수 필드·enum·자료형을 고정하고, 스키마 버전 변경 시 기존 결과를 읽을 수 있는지 검사한다. 데이터 형식은 먼저 확정해 샘플 화면·수집 검증을 진행할 수 있다. **구축 순서 5단계 전 결정** 대상인 판정 세부값은 미정 상태를 표현하고, 이를 임의 기본값으로 채우거나 실제 판정 가능으로 표시하지 않는다. 미정 판정값 때문에 1~4단계의 구조·화면 작업 전체를 막지는 않는다.

**S6 검증 범위와 한계**

- 코드 검사: 스키마, 섹션·세부 항목 누락/중복, 참조 무결성, 기간·단위, 계산 재현, 근사 표기, v1 사업 품질 종합·성장률 경계·강제 회피→보류→판정표 재적용, 도식 구문, 사이트 빌드와 산출물 간 일관성. 성장률 하단/기본/상단의 순서·비교 대상 일치와 할인율 9%/10%/11% 결과 구분도 검사한다.
- 근거 검토: 인용이 주장·해석을 뒷받침하는지, 반대 논거와 틀릴 수 있는 조건이 관련 있는지 검토하고 결과를 기록한다. URL 존재·접속 성공만으로 사실 확인 완료라고 표시하지 않는다. AI의 근거 검토도 진실성을 보증하지 않는다.
- **v1 기본값 (Codex 제안):** 모든 필수 응답과 최종 판정·핵심 논거·반대 논거·수치에는 추적 가능한 근거가 있어야 한다. 원문이 주장과 맞지 않거나 인용을 확인하지 못하면 통과시키지 않는다. 쓰기 단계와 분리한 근거 검토를 수행하고 실패한 항목만 최대 2회 수정·재검토한 뒤 남은 오류가 있으면 게시를 차단한다. 선택 항목은 근거가 없으면 확인 불가로 전환할 수 있지만 필수 근거의 실패를 경고로 낮추지 않는다. 403·429로 재접근이 안 되더라도 기존에 확보한 원문·해시·위치로 검토할 수 있으면 단순 링크 접속 실패와 내용 실패를 구분한다.
- 값이 `unavailable`인 것과 산출물이 미완성인 것을 구분한다. 명시된 누락 허용 기준을 충족하는 완성 보고서는 판정 보류로 게시할 수 있다. 필수 응답·출처 누락, 수치·판정 불일치, 규칙 미정, 빌드 실패는 게시 오류이다.
- 검증 완료 후 파일이 바뀌면 해시를 대조해 재검증한다. `--viz-only`도 도식 외 기존 보고서·판정이 변하지 않았는지 확인한다.

**확장성 원칙**

- **템플릿 변경:** `report.md`의 섹션은 `<!-- section:s05 -->` 같은 고정 ID로 구분한다. 목차는 해당 결과의 템플릿 버전에 맞는 `sections.json`, 세부 검증은 `template-items.json`을 본다. 버전이 다른 결과에 최신 템플릿을 무조건 적용하지 않는다.
- **엔진:** 실행 환경이 엔진을 자동 기록해 `claude/` 또는 `gpt/` 폴더에 저장한다. 두 폴더가 다 있으면 웹에 전환 버튼과 비교 탭이 나타난다.
- **산업 연동 — v1 기본값 (Codex 제안):** 산업 슬러그는 영문 소문자 kebab-case(`^[a-z0-9]+(?:-[a-z0-9]+)*$`, 예: `power-generation`)로 고정하고 공통 슬러그 목록에서 선택한다. 미분류는 `unclassified`, 기존 슬러그는 표시명 변경과 별개로 유지한다. 이후 산업분석 데이터가 같은 슬러그로 들어올 때만 링크를 노출한다.
- **파일명:** 다운로드용 내보내기 파일은 기존 규칙대로 `020.기업분석_[영문 정식명]_C`로 저장한다(GPT판은 \_GPT 접미사, Gemini와 헷갈리는 \_G는 쓰지 않음). 덮어쓰기 방식이므로 날짜는 파일명이 아니라 `meta.json`에 둔다.

## 웹사이트 설계

사이트는 기업 목록 페이지와 기업 상세 페이지 두 종류로 구성하고 정적 사이트 생성기로 `data/`를 읽는다. **v1 기본값 (Codex 제안):** Astro의 정적 출력을 사용하고 인증은 Pages Functions에 둔다. 설치·빌드 실험에서 확인한 의존성 버전과 잠금 파일을 고정하고 문제가 확인될 때 변경한다.

**기업 목록 페이지**

- 분석한 기업을 카드로 나열한다: 티커, 영문명, 엔진별 판정 칩(예: C 관망 · G 매수 검토), 분석일.
- 판정과 산업으로 필터링한다. 산업 필터는 산업분석 연동을 위한 자리이기도 하다.

**기업 상세 페이지 — 상단 대시보드**

1. 헤더: 기업명·티커, 코드가 결정한 판정 배지(매수 검토 / 관망 / 회피 / 판정 보류), 분석 기준시점, 엔진 전환 버튼(Claude | GPT, 버튼마다 그 엔진의 판정·기준시점). 두 엔진의 판정이 다르면 "판정 엇갈림" 칩을 띄우되 입력·기준 버전이 다르면 함께 알린다. 스크롤하면 이 줄만 남아 화면 위에 고정된다.
2. 주가 차트: TradingView 무료 임베드 위젯. 위젯의 갱신·지연 상태와 고정 스냅샷을 구분하고, 차트 아래에 "아래 수치는 YYYY-MM-DD 거래일 종가 기준"이라고 실제 거래일을 표기한다. 주가가 없으면 확인 불가 사유를 표시한다.
3. 분석 기준 스냅샷 (분석일 고정): 분석 기준일 주가, 시가총액, PER(TTM), EPS(TTM), 52주 범위, 베타(5년 월간), 배당·수익률, 배당락일, 다음 실적 발표일.
4. **v1 기본값 (Codex 제안):** 재무분석 카드는 기존 6개를 유지한다. 매출 성장률(최근 연도·3년 CAGR), 영업이익률, OCF 성장률, 잉여현금흐름(OCF − CapEx), 부채비율, 순이익의 질(OCF ÷ 순이익)을 분석일 기준으로 표시한다. 재고나 매출채권이 매출보다 빠르게 늘면 카드 줄 위에 경고 배지를 띄운다. 계산 불가 카드를 임의의 다른 지표로 교체하지 않고 상태를 표시한다.
5. 축 A·축 B 결과, 코드가 적용한 판정 사유 한 단락 + 관련 평가의 틀릴 수 있는 조건. 판정 기준 v1·'실제 결과 검토 후 조정 예정', 우선 규칙 적용·판정 보류·근사값 사용 여부를 표시한다. 가격 평가에는 10% 할인율의 요구 성장률과 AI의 하단/기본/상단, 할인율 9%·11%의 민감도 결과를 함께 제공한다.
6. 접이식 줄: 핵심 논거·반대 논거, 매도 트리거.

실시간 시세 칸(호가·거래량 등)과 애널리스트 목표주가는 넣지 않는다. 목표주가는 판정을 그 숫자 쪽으로 끌어당길 위험이 있어서다.

**기업 상세 페이지 — 하단 탭**

- **보고서:** 16개 섹션 본문. 왼쪽에 섹션 목차 사이드바를 두고, 휴대폰에서는 드롭다운으로 바꾼다. \[해석\] 문장과 반대 논거는 색으로 구분한다.
- **재무:** 지표별 카드 12개. 시계열이 유효한 항목에는 3년 추이 차트(Chart.js)를 표시하고, 부채 만기·금리 비중 등은 데이터에 맞는 표·도식으로 표시한다. 코드가 만든 수치 줄과 AI 분석(\[해석\]·틀릴 수 있는 조건·출처), 맨 아래 재무 종합 요약을 둔다. 경고 신호는 상단에 모으고 계산 불가·해당 없음·근사는 구분한다.
- **시각화:** 플라이휠, 사업 구조·밸류체인 도식. Mermaid로 브라우저에서 그리고 PNG 다운로드 버튼을 둔다. `--no-viz`로 분석했으면 "미생성"을 표시한다.
- **템플릿:** 이 기업에 적용한 템플릿 전문과 버전, AI가 분류한 기업 유형·분류 근거·적용 잣대·판정 기준 v1을 표시한다. 원본 대비 수정·추가된 항목을 색과 텍스트로 표시하고 바꾼 이유를 붙인다. `--original`이면 원본 템플릿 전문과 "원본 템플릿 사용" 표시를 제공하며, 기업 유형·평가 잣대 표시도 유지한다.
- **출처·데이터:** 섹션별 출처 링크, 수치별 원천(공시명·태그), '확인 불가' 항목 목록.
- **비교 (두 엔진 분석이 모두 있을 때만):** 최종 판정·적용 규칙, 축 A·축 B 결과, 다섯 고정 점검 항목의 평가·근거·틀릴 수 있는 조건, 역DCF 요구 성장률과 AI의 달성 가능 성장률 하단/기본/상단, 코드의 가격 등급, 강제 회피 조건의 확인 상태·근거를 나란히 보여준다. 할인율 10%의 기본 결과와 9%·11%의 민감도 결과를 구분한다. **두 엔진이 어느 항목에서 갈렸는지** 강조하고 핵심 논거·반대 논거·매도 트리거·커스텀 템플릿 차이도 제공한다. 입력 데이터 식별자·기준시점·기업 유형·분류 근거·코드·판정 기준 버전(v1)을 비교 상단에 표시한다. 조건이 다르면 '입력/기준 차이 있음'으로 표시해 엔진 판단 차이로 단정하지 않는다. 재무 수치의 전면 비교 차트는 v1에서 제외하되 입력 차이의 상세 출처는 확인할 수 있게 한다.

**공통**

- 휴대폰에서도 볼 수 있게 반응형으로 만들고, 라이트/다크 모드를 지원한다.
- 합성 데이터는 '샘플·실제 투자 판정 아님'을 명확히 표시하고 실제 분석과 구분한다. 미정 규칙을 샘플 값으로 확정한 것처럼 저장하지 않는다.
- 엔진 전환 버튼과 비교 탭은 두 엔진 분석이 모두 있을 때만, 산업 링크는 산업 데이터가 있을 때만 나타난다. 기업 페이지는 방문자가 마지막에 본 엔진을 브라우저에 기억해 먼저 보여주고, 처음 방문이면 더 최근에 분석한 쪽을 보여준다.

## 호스팅·게시·접근 제어

게시는 "검증 완료 산출물 → 사이트 저장소 커밋·푸시 → Cloudflare Pages 빌드 → 해당 커밋의 실제 배포 확인"으로 진행한다. 서버 상시 운영 없이 무료 한도 내에서 운영한다. Functions 한도 초과 시 인증을 우회해 서비스하지 않고 차단한다. Railway는 서버 측 계산이나 DB가 필요해질 때를 위해 남겨 둔다.

**로컬 우선 구조**

사이트 화면 코드는 플러그인의 `site/`에 함께 두고 유일한 원본으로 삼는다. JSON·Markdown 등 로컬 산출물은 게시 설정과 관계없이 보존한다. 게시 설정이 없으면 같은 화면의 로컬 미리보기를 빌드해 위치를 안내하고 정상 종료한다. 게시 설정이 있으면 로컬 미리보기 생성은 생략할 수 있지만 S6의 데이터·렌더링 검증은 생략하지 않는다. 배포용 빌드는 Cloudflare가 수행하고 완료를 별도로 확인한다.

- 화면은 항상 플러그인의 `site/` 폴더에서 고친다. 사이트 저장소의 화면 코드를 직접 고치면 다음 게시 때 플러그인 쪽 코드로 덮어써진다.
- 게시할 때 플러그인 화면 코드와 사이트 화면 코드를 비교한다. **v1 기본값 (Codex 제안):** 운영에는 dev 검증·승격 기록이 있는 화면 버전만 동기화하며 미검증 화면 변경이 있으면 운영 화면을 교체하지 않고 개발 경로를 안내한다. 일반 분석의 검증된 데이터 자동 게시는 유지한다.
- 분석 없이 화면 수정만 바로 반영하려면 `/company-publish --site`를 쓴다.
- HTML은 빌드 도구가 만들고 AI는 구조화 응답과 평가를 작성한다. HTML을 AI가 매번 작성하지 않지만, 검증·수정·재시도에는 사용량이 발생할 수 있다.
- 화면 동기화는 허용된 화면·빌드 파일만 대상으로 하고, 분석 데이터·배포 비밀 값·사이트별 설정은 덮어쓰지 않는다. 코드 버전과 데이터 스키마 호환성을 확인해 오래된 플러그인이 최신 사이트를 무조건 되돌리지 않게 한다.
- 다른 사용자에게 내 저장소 쓰기 권한을 주는 방식은 쓰지 않는다. 저장소 전체를 고치거나 지울 수 있고, 같은 티커를 서로 덮어쓰게 되기 때문이다.

과제가 끝난 뒤 처음 설계(화면 코드는 사이트 저장소, 로컬 미리보기 없음)로 되돌릴 수 있게, 로컬 미리보기와 화면 동기화 코드는 각각 별도 모듈로 분리해 두고 게시 스크립트는 그 모듈을 호출만 하게 만든다.

**게시 절차**

1. 대상 저장소·브랜치·엔진·run_id와 S6 검증 당시의 산출물 해시를 확인한다. **v1 기본값 (Codex 제안):** 개발 미리보기 브랜치는 `dev`, 운영 브랜치는 `main`이다. 브랜치를 이름 추측이나 현재 체크아웃 상태로 선택하지 않는다.
2. 대상 저장소의 원격 최신 상태를 확인하고, 검증 완료 묶음을 `data/companies/<티커>/<engine>/`에 반영한다. 파일별 중간 상태를 게시하지 않는다. 다른 엔진·티커·사용자의 변경을 덮어쓰거나 관계없는 변경을 함께 커밋하지 않는다.
3. `analysis: RKLB <engine> 2026-10-06 <run_id>`처럼 대상이 식별되는 메시지로 커밋·푸시한다. 같은 작업 영역의 동시 게시에는 잠금을 사용하고, 다른 실행의 원격 변경은 충돌 검사로 감지한다. 강제 푸시로 해결하지 않는다.
4. 오래된 실행이 최신 기준시점의 결과를 교체하거나 `--viz-only`의 기준 보고서가 바뀌었으면 중단한다. 충돌 해결 후에는 대상 변경분의 검증을 다시 수행한다.
5. Cloudflare 빌드 후 **공개 빌드 정보 파일의 커밋 해시 확인 방식부터 검토·실증**한다. 사이트 자격 증명 없이 대상 주소의 `/build-info.json`을 읽어 기대 커밋·엄격한 파일 형식을 확인한 뒤 해당 커밋의 배포 완료로 표시한다. 기업 페이지·접근 제어 검증은 S6와 개발 배포 검증에서 별도로 수행하며, 공개 해시 확인만으로 인증·화면 검증까지 통과했다고 표시하지 않는다. 단순 푸시 성공이나 일정 시간 경과로 완료 처리하지 않는다.
6. 실패·시간 초과·해시 불일치는 `게시 실패` 또는 `배포 미확인`으로 남기고 마지막 확인된 정상 배포와 구분한다. 새 정상 배포가 확인되기 전에는 기존 정상본을 완료본으로 취급한다. 인증·화면 오류가 있는 새 배포가 노출된 경우에는 이전 정상 배포로 복구한 뒤 복구 결과도 확인한다.
7. 이전 분석본은 기본 화면에서 최신본으로 대체하되 깃 이력에 보존한다. 복구는 대상 실행의 변경만 되돌려 다른 엔진·기업의 최신 결과가 함께 사라지지 않도록 한다.

**빌드 정보 파일을 통한 배포 확인 — 우선 검토안**

- **사용자 확정:** `/build-info.json`은 커밋 해시(`commit_sha`)와 빌드 시각(`built_at`, UTC 시각) 두 필드만 담는다. 사이트 빌드 시 `CF_PAGES_COMMIT_SHA`의 **사이트 저장소 빌드 커밋 전체 해시**와 빌드 시각을 생성하며, 해시 변수가 없으면 배포 빌드를 실패시킨다. 다른 필드·기업 정보·환경 설정·비밀 값은 넣지 않는다. 플러그인 저장소 해시와 구분하고, 파일 생성 때문에 다시 커밋하는 순환 구조는 만들지 않는다.
- **사용자 확정:** 이 정확한 파일 경로는 비밀번호 보호에서 제외해 공개한다. 개발 미리보기는 해당 `dev` 배포 주소, 운영은 실제 운영 주소에서 쿠키·사이트 자격 증명 없이 확인한다. 상위 디렉터리나 다른 JSON 파일로 예외를 넓히지 않는다. 배포 확인용 사이트 자격 증명 저장·조회 항목은 두지 않는다. GitHub 푸시·Cloudflare 관리에 필요한 권한은 별개이다.
- 로그인 HTML이나 HTTP 200만으로 성공 처리하지 않고 JSON의 두 필드·자료형·시각 형식·기대 커밋 일치를 검사한다. 추가 필드는 오류로 처리한다. 캐시로 이전 해시가 남지 않도록 `Cache-Control: no-store`와 실제 응답을 검증한다.
- **v1 기본값 (Codex 제안):** 푸시 후 15초 간격, 최대 10분 동안 공개 빌드 정보의 JSON·커밋 해시를 확인한다. 개별 HTTP 요청 제한은 10초이며 전체 10분 안에 포함한다. 401·403은 공개 경로 설정 오류로 즉시 중단하고 사이트 로그인을 시도하지 않는다. 네트워크 오류·이전 해시는 제한 내 재시도한다. 시간 초과는 실패 확정이 아닌 '배포 미확인'이며 자동 재푸시·자동 성공 처리하지 않는다. 후속 재확인으로 상태를 갱신할 수 있다.

**개발·검증용 경로 — dev 브랜치 미리보기**

- `research-site`의 `dev` 브랜치를 Cloudflare Pages 미리보기로 배포한다. 사용자용 테스트 옵션은 추가하지 않고 개발 설정과 브랜치로 경로를 분리한다. 샘플과 검증용 결과는 운영 결과로 자동 승격하지 않는다.
- 미리보기 런타임에도 동일한 비밀번호 보호 정책·필요한 비밀 설정을 적용한다. 운영 설정이 미리보기에 자동 상속된다고 가정하지 않는다. 설정 누락은 접근 차단으로 처리한다.
- 검증 순서: ① 쿠키 없는 접속·잘못된 비밀번호에서 목록/상세 HTML·분석 데이터·다운로드가 내려오지 않는지 ② 올바른 비밀번호로 정상 열리는지 ③ 30일 만료·변조·비밀번호 변경 전 쿠키가 거절되는지 ④ `dev` 별칭과 배포별 고유 주소 모두 같은 보호 정책인지 ⑤ `/build-info.json`만 쿠키 없이 읽히고 커밋 해시·빌드 시각 외 필드가 없으며 기대 커밋과 일치하는지 검사한다.
- 미리보기 주소의 보호 실패는 운영 반영을 막는 오류이다. 운영 최초 배포와 인증 코드 변경 시에도 같은 검사를 수행한다. 이전 배포 주소가 남는 경우에도 비공개 조건이 유지되는지 확인한다.
- **v1 기본값 (Codex 제안):** 화면·스키마·인증 같은 개발 변경은 dev의 샘플·회귀·비밀번호·커밋 해시 검증 후 `dev → main` PR로 검토·병합한다. 샘플 결과와 운영 기업 데이터는 승격 변경분에서 제외하고, 병합 전 최신 main을 반영해 운영 분석을 잃지 않게 한다. 일반 사용자의 `/company`는 이미 검증된 버전으로 생성한 데이터만 main에 자동 게시하며 매 분석마다 PR 승인을 요구하지 않는다.

**접근 제어 (비밀번호)**

- 사이트는 일반 경로로 둔다 (예: `…pages.dev/RKLB`).
- Cloudflare Pages Functions 미들웨어가 로그인에 필요한 최소 경로와 공개 `/build-info.json`을 제외한 보호 대상 요청 앞에서 비밀번호를 확인한다. 비밀번호·세션 서명 비밀 값은 Cloudflare 비밀 설정에 저장하고 코드·저장소·빌드 산출물에는 넣지 않는다.
- **사용자 확정:** 세션은 로그인 후 절대 만료 **30일**, 자동 연장 없음으로 한다. 비밀번호 원문 대신 서명된 만료 세션을 `HttpOnly`·`Secure`·`SameSite=Lax`·호스트 전용 쿠키로 전달한다. 쿠키 유지 기간도 30일로 설정하고 서버가 서명의 만료시각을 검증한다. 비밀번호 변경 시 세션 버전·서명 비밀 값을 교체해 기존 세션을 무효화한다. 운영·미리보기·과거 배포 주소의 적용 상태를 확인하고 이전 비밀 설정을 쓰는 주소는 접근을 차단한다.
- 보호 대상에는 HTML, 분석 JSON·Markdown·도식, 다운로드를 포함하며 운영 도메인·pages.dev·미리보기 별칭·고유 배포 주소에 같은 정책을 적용한다. `/build-info.json`만 지정된 공개 예외로 두고 HTML만 가려 놓거나 다른 정적 데이터 경로를 열어 두지 않는다. 인증 후 응답이 공개 캐시에 저장되어 우회되지 않는지도 확인한다.
- Functions 호출 경로에서 보호 파일이 제외되지 않게 하고 **fail closed**로 설정한다. 무료 요청 한도 초과·인증 설정 누락·미들웨어 오류 시 보호 콘텐츠를 제공하지 않는다. 공개 `/build-info.json`은 이 보호 파일 집합에서 제외한다. noindex와 robots.txt는 접근 제어를 대신하지 않는다.
- AI가 만든 Markdown·Mermaid를 렌더링할 때 실행 가능한 HTML·스크립트·위험한 링크를 허용하지 않도록 정화·렌더러 설정을 검증한다.
- **사용자 확정:** 로그인 실패 횟수 제한과 별도 Worker·Durable Object는 v1에서 제외한다. 배포 문서에는 비밀번호 생성기로 만든 충분히 긴 무작위 문자열을 공용 비밀번호로 사용하도록 안내한다. 실제 비밀번호는 안내 문서·로그·저장소에 기록하지 않는다. 서명된 쿠키 검증과 잘못된 비밀번호 거절은 유지한다.
- 화면에서 자바스크립트로만 가리는 방식은 쓰지 않는다. 그 방식은 페이지 원문이 그대로 내려받아져 우회된다.
- 모든 페이지의 noindex와 `robots.txt` 차단은 유지한다.
- 사이트 저장소는 비공개로 둔다.
- 비밀번호는 사이트를 "보는" 권한일 뿐이다. 플러그인을 설치한 다른 사람이 이 사이트에 게시하려면 비공개 저장소에 푸시할 권한이 필요하므로 불가능하다. 다른 사용자는 설정 파일에 자기 저장소·사이트를 지정해 각자 게시한다.

**나중에 검토**

- 로그인 실패 횟수 제한. 별도 Worker·Durable Object 등 구현 방식과 제한값은 도입 시 검토하며 v1 의존성·구축 완료 조건에 포함하지 않는다.

## 저장소 구조와 작업 환경

저장소는 둘로 나눈다. 플러그인은 마켓플레이스 등록·조교 공유가 가능해야 하고, 사이트는 분석 결과가 담겨 비공개여야 하기 때문이다.

**사용자 확정:** 마켓플레이스는 사용자의 공개 GitHub 저장소에 직접 구성한다. 공식 디렉터리 심사 승인은 완료 요건으로 두지 않는다. 엔진별 등록 형식·설치 경로는 2단계에서 로컬로 검증하고, 3단계에 공개 저장소를 만든 뒤 실제 저장소 기반 설치를 확인한다. GitHub 계정은 있고 Cloudflare 계정은 없다. Cloudflare 계정 준비와 공개 플러그인/비공개 사이트 저장소·Pages 프로젝트 생성은 3단계에서 수행한다. 아래 저장소 이름은 설계상 이름이며 실제 식별자는 생성 시 기록한다.

| 저장소 | 공개 여부 | 내용 |
| --- | --- | --- |
| `company-analysis-plugin` | 공개 | 공통 스킬·수집·계산·판정·검증 스크립트, 템플릿·스키마·규칙, 환경별 패키징·실행 어댑터, 사이트 화면 코드(로컬 미리보기와 웹 공용). 실제 runs/·분석 결과·비밀 값은 공개 저장소에 포함하지 않음 |
| `research-site` | 비공개 | `data/` 분석 결과와 배포 설정. 게시 때 데이터를 받고, 화면 코드는 플러그인 쪽이 바뀌었을 때만 함께 받는다. 산업분석도 나중에 여기 합류 |

**작업 환경 (Windows PC)**

- 수집·계산·검증 스크립트는 Python으로 작성하고 Windows에서 그대로 돌아가는지 확인한다 (경로 구분자, 한글 인코딩 UTF-8).
- 로컬 미리보기를 만들려면 Python과 Node.js가 필요하다. 조교 PC에도 둘 다 설치되어 있어야 한다. 웹 게시본의 빌드는 Cloudflare가 한다.
- 비밀 값(SEC용 연락처 이메일, 주가 API 키, 사이트 저장소 경로)은 `.env` 파일에 두고 깃에 올리지 않는다.
- 플러그인은 Codex에서 개발하고, 분석은 Claude Code(Claude판)와 Codex(GPT판) 양쪽에서 실행한다. 두 환경 모두 웹 검색이 켜져 있어야 한다.

**두 환경의 초기 호환성 확인**

- 공통 `SKILL.md`와 스크립트는 공유하되 설치 메타데이터, 스킬 호출명, 경로 해석, 엔진 기록, 도구 접근·권한은 환경별 어댑터에서 처리한다. 공유 문서가 있다는 이유로 실행 호환성을 보장하지 않는다.
- **v1 기본값 (Codex 제안):** Codex는 루트 `plugin.json`의 portable 형식, Claude Code는 `.claude-plugin/plugin.json` 메타데이터를 사용한다. 공통 `skills/`·스크립트·버전 원본에서 배포 메타데이터를 생성해 내용이 갈라지지 않게 한다. 등록 대상이 요구하면 `.codex-plugin/plugin.json` 호환 패키지도 생성한다. 사용자 공개 저장소의 자체 마켓플레이스에서 두 엔진의 실제 설치·호출을 검증한다.
- 처음부터 양쪽에서 설치 → 실제 스킬 호출 → Windows의 Python 실행 → 샘플 JSON 생성 → 검증을 확인한다. Node.js 빌드, 한글 경로·공백 경로, 웹 검색·공시 접근, 게시 권한도 단계적으로 확인하고 확인한 버전을 기록한다.
- 사용자 계정의 권한·샌드박스·요금제 제한 때문에 발생하는 승인·한도는 플러그인이 우회하지 않는다. '중간 사용자 확인 없음'은 필요한 권한과 설정이 준비된 정상 실행 경로를 뜻한다.

## 개발 스택

스택은 네 가지 원칙으로 골랐다. 기존 구독과 무료 서비스 한도 내에서 운영할 것, 수치 계산과 최종 판정은 코드가 수행하고 해석·항목 평가는 AI가 작성할 것, 결과와 근거를 텍스트 파일로 남길 것, 과제 요건(마켓플레이스 등록, 조교 사용, 웹 배포)을 채울 것. 사용량 한도·외부 서비스 조건은 실제 계정과 배포 실험에서 확인한다. 누락된 스택 임베드 도식 대신 아래 표를 기준으로 사용한다.

| 층 | 선택 | 검토한 대체재 | 고른 이유 |

Twelve Data·Astro·플러그인 배포 형식은 위의 v1 기본값으로 시작한다. 실제 데이터 범위·표시 권한·설치·빌드 검증에서 문제가 확인되면 근거와 대안을 기록해 교체할 수 있다. 무료로 접근할 수 있다는 것과 웹에 표시할 권한이 있다는 것은 별도로 확인한다.

## 구축 순서

과제 시연을 위해 **데이터 계약이 확정되면 샘플 화면 작업을 실제 수집·계산 작업과 병행할 수 있다.** 화면을 모두 완성한 뒤 숫자 검증을 시작하지는 않는다.

1. **문서·데이터 계약 확정:** 사용자 확정 지원 범위와 v1 기술 기본값으로 JSON Schema·고정 항목 ID·버전·상태를 정의한다. 스키마는 **v1 초안**으로 두고 4단계 RKLB 실제 공시 데이터 검증 통과 전까지 수정 가능하다. 16단계 템플릿은 입력 완료이며 16개 섹션 ID·제목을 원본에서 추출한다. 투자 프레임워크 v2는 입력 대기. 판정 세부 TODO(기존 질문 1~3)는 **구축 순서 5단계 전 결정**으로 남기며 이번 일정의 판정은 **판정 보류 (v0.1)**로 고정한다. 완료 기준은 샘플·누락·근사·미정 상태를 같은 계약으로 표현하고 검사할 수 있는 것.
2. **두 엔진 초기 실행·API 제공 범위 확인:** Claude Code와 Codex 각각 로컬 패키지 설치·호출·Python 실행·샘플 JSON 생성·검증까지 확인한다. Windows 경로·인코딩·설치 버전·권한 차이를 기록한다. Twelve Data 무료 요금제에서 배당 이력·실적 발표 일정 제공 여부를 각각 확인하고, 미제공이면 배당은 SEC 공시·발표일은 웹 리서치로 대체하는 경로를 검증한다. 계정/API 키가 없어 확인하지 못했다면 미확인으로 기록하며 무료 제공으로 간주하지 않는다. 전체 분석을 구현한 뒤 Codex 호환성을 확인하는 순서는 사용하지 않는다.
3. **병행 A — 저장소 준비·샘플 화면·개발 배포:** 데이터 계약 확정 직후 샘플 화면 작업 시작 가능. 기존 GitHub 계정으로 공개 플러그인 마켓플레이스 저장소·비공개 사이트 저장소를 만들고 Cloudflare 계정과 Pages 프로젝트를 준비한다. 두 엔진의 실제 공개 저장소 등록·설치를 확인한다. 명확한 샘플 표시가 있는 RKLB Claude판·GPT판으로 목록·상세·비교 화면과 판정 보류·근사·항목 불일치 상태를 만든다. 배포 안내에 충분히 긴 무작위 비밀번호 사용을 명시한다. `dev` 브랜치 미리보기로 배포하고 휴대폰 화면, 동일 비밀번호 보호, 서명된 30일 쿠키·비밀번호 변경 시 무효화, 미인증 원본 접근 차단, 공개 빌드 정보 두 필드·커밋 해시 기반 배포 확인을 검증한다.
4. **병행 B — 실제 재무 수집·계산·검증:** RKLB 한 기업의 실제 공시 → 정규화 → 계산 → S6 수치 검증 → 최소 화면 연결을 먼저 완주한다. 이후 결산월이 다른 기업 3곳 이상과 아래 예외 사례로 확장한다. 샘플 화면 완성을 기다리지 않는다.
5. **평가·판정 및 분석 파이프라인:** 이번 일정은 사용자 지시대로 판정 엔진(항목 평가·역DCF·강제 회피·판정표)을 구현하지 않고 `판정 보류 (v0.1)`를 유지한다. 16단계 템플릿과 실제 공시 스냅샷을 연결한 단순 보고서부터 구현한다. 아래 판정 기준 v1과 미정 세부 TODO는 후속 작업으로 보존한다.
6. **이어하기·시각화·옵션:** 체크포인트 재사용·무효화, 신규 실행과 재개 구분, Mermaid, `--no-viz`·`--viz-only`·`--original` 및 잘못된 조합을 검증한다. 도식 재생성 중 보고서가 바뀌면 갱신을 차단하는지도 확인한다.
7. **자동 게시·실패 복구:** `/company-publish`, 화면 동기화, 동시 게시 충돌, 오래된 실행 차단, 배포 성공/실패/미확인, 이전 정상본 복구를 `dev`에서 확인한다. 검증된 개발 변경을 정해진 절차로 운영에 반영하고 운영 인증·빌드 정보도 다시 확인한다. 사용자 분석의 기본 자동 게시 흐름은 유지한다.
8. **마감:** 모바일·두 엔진 전환·항목별 비교, 키 없는 조교 PC의 로컬 경로, 설치 안내, 비밀 값 미포함, 사용자 공개 저장소의 자체 마켓플레이스 등록·설치를 점검한다.

**1단계 착수 가능 여부와 계획**

현재 남은 TODO 중 **1단계 착수를 막는 항목은 없다.** 판정 세부 기준은 5단계 전 결정하고, 템플릿 원본은 입력 완료, 투자 프레임워크 v2는 입력 대기다. 1단계에서 실제 16개 섹션 ID·제목과 나머지 데이터 형식·미정 상태를 정의한다. API 권한 확인은 2단계, 계정·저장소·Pages 생성은 3단계에서 처리한다.

1. 파일별 책임·생성 주체·공통 ID·버전·단위·기간·누락/근사 상태를 데이터 사전으로 정의한다.
2. 실행·출처·지표·평가·역DCF·판정·화면·템플릿·검증 결과의 JSON Schema와 공개 빌드 정보의 두 필드 전용 스키마를 작성한다.
3. 명시적인 합성 샘플로 정상·누락·근사·확인된 강제 회피·규칙 입력 대기·두 엔진 불일치를 표현한다. 실제 템플릿으로 오인할 샘플 항목은 만들지 않는다.
4. 스키마 검사와 파일 간 참조·실행/입력 일치 검사를 구현하고 유효/무효 사례를 검증한다. 데이터 구조 통과와 실제 게시 가능 판정은 구분한다.
5. 호환성·미정 규칙 연결 지점을 기록해 3단계 샘플 화면과 4단계 수집 작업에 넘긴다. 자세한 작업 계획은 [1단계 데이터 계약 계획](superpowers/plans/2026-10-06-data-contract.md)에 둔다.

**구축 완료 전 확인할 대표 사례**

- 숫자: 일반 연간/분기/누적 구분, 비12월 결산, 정정 공시, 단위·통화 차이, 음수 OCF 개선, 분모 0·자본잠식, 재고 없음, 주식분할·발행주식 수 변경, 분기 EPS 누락 시 근사 및 근사 불가.
- 판정: 표의 9개 칸, 사업 품질 약함 우선·강함 3개 경계, 요구 성장률이 하단 미만/하단과 같음/기본과 같음/기본 초과인 경우, 할인율 9%·10%·11% 결과 구분, 주가·3년 재무·역DCF 입력 부족, 확인된 강제 회피와 입력 부족의 동시 발생(회피 우선), 미확인 위험을 발동시키지 않는지, 추가 강제 회피 네 조건과 현금 소진 기간 12개월 경계, 유형별 기준·템플릿 표시, 동일/상이한 스냅샷의 엔진 비교.
- 운영: 중단 후 재개, 원본·템플릿·규칙 변경에 따른 무효화, 동시 푸시, 도식 기준본 변경, dev/운영 미인증 요청·변조/30일 만료/비밀번호 변경 전 쿠키, 인증 설정 누락, 공개 빌드 정보의 두 필드 제한·자격 증명 없는 조회, 빌드 실패·이전 커밋 해시·배포 확인 시간 초과.
- 각 검증은 기대 결과와 실제 결과를 남긴다. 미정 조건은 통과로 간주하지 않고 해당 기준 확정 후 확인한다.

## 미결정 사항

판정의 주요 기본값은 **판정 기준 v1**로 확정했다. **실제 결과 검토 후 조정 예정**이며, 아래 확정 사항을 다시 미정 항목으로 취급하지 않는다.

- [x] **판정표:** 제시된 표 그대로 사용.
- [x] **역DCF 기본값:** 할인율 10%, 영구성장률 2.5%, 예측 기간 10년. 할인율 9%·11% 결과도 함께 표시.
- [x] **가격 경계:** AI가 달성 가능 성장률 하단/기본/상단을 제시. 코드가 요구 성장률을 비교해 하단 미만은 여유 있음, 하단~기본(양 끝 포함)은 적정, 기본 초과는 과도로 분류.
- [x] **사업 품질 종합:** 회계 품질 또는 재무 안정성 약함, 혹은 약함 2개 이상이면 약함. 그 외 약함 없이 강함 3개 이상이면 강함, 나머지는 보통.
- [x] **적용 순서:** 확인된 데이터에 따른 강제 회피 → 판정 보류 → 판정표. 데이터 부재를 위험으로 추정하지 않음.
- [x] **기업 유형:** AI가 근거와 함께 분류해 템플릿 탭에 표시. 성장형·적자, 경기순환형, 턴어라운드형은 본문의 v1 잣대로 분기하고 그 외에는 기본 잣대 적용.
- [x] **추가 강제 회피:** 감사인의 계속기업 불확실성 의견, 최근 3년 내 재무제표 정정, 내부통제 중대한 취약점 보고, 적자 기업의 현금 소진 기간 12개월 미만.

판정 세부 기준(기존 질문 1~3)은 지금 정하지 않고 **구축 순서 5단계 전 결정**으로 보류한다. 기술 사항(기존 질문 4~8 및 9~10의 기술 선택)은 **v1 기본값 (Codex 제안)**으로 채웠으며, 이후 사용자가 지정한 인증·배포·API 대체 사항은 **사용자 확정**으로 구분했다. 제안 기본값은 실제 데이터·배포 검증에서 근거를 남기고 조정할 수 있다. 사용자가 확정한 판정값·지원 범위·변경 사항을 임의 제안값으로 취급하지 않는다.
